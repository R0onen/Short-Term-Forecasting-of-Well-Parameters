# Student 2 implementation plan — Forecasts and evaluation

## 1. Project context

Short-Term Forecasting of Well Parameters is a three-person AI Programming project using the NK Oil Well Sensor Monitoring v2 hourly archive. Student 1 builds the Pandas/SQLite pipeline for 10 wells. Student 2 owns course requirement E and the modeling treatment of known quality issues in B. Student 3 uses the SQLite results in Streamlit. The approved target is `pump_fillage` (%) for NK-7, NK-68, NK-77, NK-82, NK-86, NK-91 and NK-93, with horizons 1–24 hours. Compare naive, seasonal naive and direct lag-based Ridge. Additional targets and models are outside this assignment.

Use the published split from revision `4004bb78ca8811a87c2892a89e457c59d22ace2b`. Train covers 2026-01-01 00:00:00 through 2026-08-08 22:00:00. Test covers 2026-08-08 23:00:00 through 2026-09-30 23:00:00. Assume a completed hourly mean becomes available when its hour closes. The source does not establish time zone or ingestion delay. The model is fixed during backtest. Historical test observations become available sequentially.

## 3. Step-by-step development instructions

Before [SHARED CONTRACT READY](INTERFACES.md#shared-contract-ready), review the contract and supply fixture cases. Start M01 after A01 sign-off. Use the canonical fixture until the A04 database is ready.
1. **M01.** Read target values from the wide table and metadata from SQLite. Derive the supported well set from the catalog's pump-fillage entries and verify it against the seven-well list for the pinned revision. Validate uniqueness and sort by time within each well. Align each series to an exact hourly index before using positional shifts. Preserve NULL and enforce [0, 100] for usable targets, including zero. For origin `t` and horizon `h`, store `target_ts = t+h hours`, separate the actual `y[t+h]` from predictors and generate `lag_0, lag_1, lag_2, lag_3, lag_6, lag_12, lag_24` from the origin. Add `target_hour_sin` and `target_hour_cos` using the target hour of day and a 24-hour period. Store `seasonal_value = y[t+h−24]` for the baseline. The only Ridge inputs are the seven lag columns and two calendar columns. The feature builder must allow future target timestamps without observations. Fit and scoring may require a known label separately. Avoid interpolation and cross-well shifts.
2. **M02.** For naive return `lag_0` when it exists. For seasonal naive return `seasonal_value` when it exists. Each uses its own eligibility before results are intersected. Seasonal naive at `h=1` reads `t−23 hours`. At `h=24` it resolves to `t`, the same source hour as naive. For a fixed origin, a missing future fact does not invalidate a forecast.
3. **M03.** First run the [train-only diagnostic](INTERFACES.md#forecast-diagnostic-and-run-report) on NK-7 at 1 and 24 h after A04. Run the full selection only after it passes. Set the validation cutoff `V=2026-07-15 00:00:00`. Internal fit requires complete inputs and observed targets with `target_ts < V`. Validation uses `V <= target_ts < test_start` and `origin_ts >= V−1 hour`. For NK-7, every fit lag and target must be on or after 2026-06-01 00:00:00, including on final refit. For each candidate alpha in 0.1, 1.0 and 10.0, fit a fresh `Pipeline(StandardScaler, Ridge)` on each well/horizon group. Score all candidates on the same eligible validation keys, clip Ridge to [0, 100] and average group MAEs with equal weight. In a tie prefer 1.0 if tied, otherwise the smaller tied value. Record the chosen alpha and validation summary. Refit each pipeline on eligible rows with `target_ts < test_start`. Keep fitting, scaling and selection insulated from test values. Require at least one usable example per internal fit, validation and final fit group. In the full official run this applies to all 168 groups. On empty or non-finite results, stop before publication and report well, horizon, stage and count. When fit succeeds and test has no common key, publish the required zero-count metric rows. For fixtures, derive the well set from applicable target series present in the fixture catalog and pass fixture-specific dates.
4. **M04.** Use `origin_ts >= test_start−1 hour` and targets within the official test interval. At the first origin, all fit labels through the last training hour are available after that hour closes. The first possible target at horizon `h` is `test_start + (h−1) hours`. Generate each method's prediction from inputs at or before the origin, with known calendar features allowed. Join the actual only for scoring. Require a known actual and all three predictions on each common key. Emit all 7 × 24 × 3 metric groups, including groups without scores. `n_actual` is all usable official test targets for the well, including those before the first allowable target for longer horizons. `n_common` is the scored-key count. Report MAE in percentage points. Discuss NK-7 separately in the results review. Use observed model results for interpretation.
5. **M05.** For each well find the latest eligible origin on or after the first test release with every usable target hour from `t−24 hours` to `t` inclusive. That window supplies seasonal values and the Ridge lags across all 24 horizons. Generate a single trajectory per model using the already refit pipelines. Ignore future actual availability when choosing the origin. Do not include these rows in the metric calculation. For the pinned archive expect NK-91 at 2026-09-29 09:00:00 and the other six at 2026-09-30 23:00:00. If no origin qualifies, emit no path rows and report it. Require an existing data DB. Calculate all outputs before the write, then replace the forecast rows for this run in one transaction using explicit inserts into Student 1's DDL. Preserve results on failure and source tables at all times. A successful rerun replaces prior rows, including a now-unavailable release. Keep the dataset build stopped during the forecast write. On success return the [run report](INTERFACES.md#forecast-diagnostic-and-run-report) and emit JSON from the full CLI. Include candidate validation evidence from the same training run.
6. **M06–M08.** Give Student 1 expected sample forecast rows early so Student 3 can build against A01. Complete component tests before reviewing U06. For the final defense show the time axis, three methods and a real comparison at horizons 1, 6, 12 and 24. Explain identical baselines at 24 h and how the loss of available keys changes coverage.

## 6. Testing

### Synthetic fixture and component checks

- Run `python -m pytest tests/test_forecast.py`. Assert missing hours stay missing in the required lag, zero survives, another well cannot affect a row, and NK-7 rows with any lag before June are excluded from fit. Check hand-computed naive and seasonal source indices at 1, 6 and 24 hours.
- Check both fit cutoffs by inspecting selected labels. Validate the earliest origins and earliest targets at 1 and 24 hours. Change values inside official test and compare alpha, scaler attributes and coefficients. For a fixed release, mutate future observations or append later hours and verify predictions agree. If actuals change, scoring can change. Use synthetic boundaries to keep these tests fast.
- With actuals 40 and 50 and predictions 35 and 55 verify MAE = 5 p.p. Remove one method's prediction and confirm the key disappears for all. Verify NULL MAE at zero common count and NULL coverage only when the denominator is zero. Test transaction rollback on insert failure and reruns without duplicate rows.
- Exercise the diagnostic with synthetic cutoffs and verify no database writes. Check candidate validation keys are identical, tie selection is deterministic, and Ridge is clipped before scoring. Remove enough history to make an internal or final fit or validation group empty and verify the existing results are retained.

### Official data and integration checks

- On the pinned build run the diagnostic before the full run. Verify diagnostic rows read only `train` and that the report and result tables remain unchanged. Compare full reruns using [the integration tolerance](TESTING_PLAN.md#fixture-и-официальные-данные), including validation results, selected alpha, fit counts, forecasts and metrics. Verify 504 metric rows and the known release origins, 72 path rows per well, exact target arithmetic, range [0, 100], and three rows per common key. Compare common counts for horizons 1 and 24 with [DATASET_ANALYSIS.md](DATASET_ANALYSIS.md#выбор-цели). Ask Student 3 to show one matching SQL/UI row and verify the visible release timestamps and end of archive together. Participate in Student 1's fixture and real-data integration checks.
