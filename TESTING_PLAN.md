# Интеграция и тестирование

Для быстрых тестов использовать небольшую SQLite fixture с двумя типами скважин, пропусками, флагами, полным отсутствием применимого параметра в одном периоде и известными значениями. Для проверки лага 24 ч добавить достаточно последовательных часов по обе стороны от искусственной границы. Даты и границы fixture передаются в тестируемые функции, а проверки на реальной ревизии используют официальный split.

## Fixture и официальные данные

Обычный `python -m pytest` использует синтетические данные, временные БД и канонический DDL. Он не требует загрузки датасета. Для A06, M06, U06–U07 и A07 владельцы дополнительно проверяют официальную ревизию по своим планам. В PR указывать отдельно команды, ревизии и результаты двух видов проверок. Для воспроизводимости на одном окружении использовать абсолютный допуск `1e-8` и относительный `1e-9` для чисел с плавающей точкой, отдельно проверять NULL и точное совпадение ключей и счётчиков.

## Сборка и передача

1. Студент 1 передаёт DDL, малую fixture и закреплённые входы. Каждый пишет компонентные тесты своего модуля. Данные фикстуры имеют заранее выписанные ожидаемые значения.
2. Студент 2 читает wide, заполняет таблицы результатов и сверяет прогнозные выходы со Студентом 3. Студент 3 проверяет EDA со Студентом 1 и ведёт отдельный тест интерфейса на реальной SQLite. Разработчики согласуют изменения интерфейсов через review.
3. Для сквозной проверки выполнить команды из [INTERFACES.md](INTERFACES.md#inputs-paths-and-commands) на чистом окружении. Студент 1 запускает CLI и pytest. Студент 2 вручную сверяет MAE для одной группы. Студент 3 воспроизводит сценарий фильтров в браузере. Пустой результат при запуске фиксируется как отдельное состояние.
4. Перед сдачей зафиксировать Git-ревизию проекта и датасета, версии библиотек и запуск, породивший SQLite. Сохранить локальную демонстрационную БД, JSON-отчёт и команды пересборки. Все трое принимают интеграцию и исправляют ошибки в своих модулях. Выходы на защите сверяются с тем же прогоном.
