# Архитектура проекта

Один Python-пакет, один локальный файл SQLite и один Streamlit entry point. Канонические схемы, ключи, сигнатуры, команды и правила владения описаны в [INTERFACES.md](INTERFACES.md). Основные зависимости — Pandas, NumPy, scikit-learn, Plotly, Streamlit, pytest и стандартный `sqlite3`. На старте согласовать одну версию Python, например 3.12, и зафиксировать проверенные версии зависимостей в `requirements.txt`.

## Поток данных и контракты

1. **CSV → исходные и очищенные данные.** `ingest.py` читает оба файла и добавляет `split` и номер исходной строки. `quality.py` сверяет схему, время, ключи, применимость и единицы. `measurements_raw` сохраняет каждую исходную запись под ключом `(source_file, source_row)`. Для проверяемой ревизии ожидается 258 387 строк. Конфликты ключа сохраняются в исходных данных и журнале, а в очищенной таблице соответствующее значение отсутствует. Повтор идентичной записи учитывается один раз с записью причины. Некорректные метки, типы и единицы фиксируются и исключаются из очищенного набора.
2. **Длинный формат → wide.** `measurements_long` содержит `well_id, timestamp, parameter, value, unit, n_obs, flag, split, is_usable`. Ключ — `(well_id, timestamp, parameter)`. Для численно корректных строк `value` хранит опубликованное значение. `is_usable` задаёт единую маску для «очищенного» EDA и ML. Флаги влияют только на соответствующий параметр. При `min_rod_weight > max_rod_weight` маскируются обе нагрузки данного часа. Нули остаются измерениями. Величины `pump_fillage` вне [0, 100] при появлении маскируются и протоколируются. `quality_issues` хранит ключ наблюдения или исходной строки, `issue_code` и принятое действие. Для сдвига площади и NK-7 журнал хранит отметки периода и дату начала.
3. **Календарь и SQLite.** `series_catalog` задаёт `(well_id, parameter)`, тип и единицу для 43 применимых пар. Каталог фиксируется по проверенной публикации. `measurements_wide` содержит `well_id, timestamp, well_type, split` и восемь колонок параметров. Ключ — `(well_id, timestamp)`. Pivot использует `value` строк с `is_usable = 1`. Маскированные и отсутствующие наблюдения становятся `NULL`. После pivot скважины приводятся к полной почасовой сетке из 65 520 ключей. Все метки хранятся как `YYYY-MM-DD HH:MM:SS` в шкале источника. `dataset_meta` хранит ревизию, границы, источник и контрольные суммы. В `measurements_long` нужен индекс `(well_id, parameter, timestamp)` для истории и `LAG`.
4. **SQL → аудит и EDA.** `gaps.sql` вычисляет предыдущую наблюдаемую метку по `(well_id, parameter)`, разницу в часах и число отсутствующих часов между ними. Для аудита наличия в расчёт входят также помеченные наблюдения. Отдельный режим `LAG` работает по уникальным часам скважины независимо от параметра. Отдельный подсчёт по календарю и каталогу выявляет краевые пропуски и пустые пары в выбранном периоде. `aggregates.sql` считает по скважине, параметру и дню или месяцу число наблюдений, среднее часовых значений, минимум, максимум, число flagged и покрытие. Для mean применяется равный вес часовых агрегатов. Политика фильтрации явно указывается в каждом выводе. [Оконные функции SQLite](https://www.sqlite.org/windowfunctions.html).
5. **Wide → оценка → SQLite.** Модуль прогноза читает `measurements_wide`, каталог и метаданные. Пишет три таблицы результатов одной транзакцией и возвращает отчёт полного прогона.
6. **SQLite → Streamlit.** `queries.py` отдаёт DataFrame с наблюдениями, масками качества и результатами. SQL ограничивает данные выбранными скважиной, параметром и временем. Графики получают эти DataFrame без обучения внутри Streamlit. Детали — в [DASHBOARD_PLAN.md](DASHBOARD_PLAN.md).

DDL и связи таблиц утверждаются на [SHARED CONTRACT READY](INTERFACES.md#shared-contract-ready).

Пайплайн строит новую БД во временном файле и заменяет рабочую после успешной сверки при остановленном Streamlit. Модуль прогноза записывает согласованный комплект результатов одной транзакцией. Перед демонстрацией последовательность запуска проверяется на чистой копии. Каждая команда владеет своим каталогом, а изменения DDL проходят совместный review владельцев данных и потребителей. Для параллельной работы применяется малая SQLite fixture со всеми таблицами. Данные fixture используются в тестах. Демонстрационная БД собирается из Hugging Face.
