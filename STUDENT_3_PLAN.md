# Student 3 implementation plan — EDA and Streamlit

## 1. Project context

Short-Term Forecasting of Well Parameters is a three-person AI Programming project using NK Oil Well Sensor Monitoring v2. The archive contains 258,387 hourly sensor rows across 10 wells from January through September 2026. Student 1 builds long and wide tables, SQL summaries and the audit. Student 2 evaluates `pump_fillage` for seven `sucker_rod_pump` wells at 1–24 hours. Own course requirements C and D and the visualization of audit requirement B. Analyze both `fountain` and `sucker_rod_pump`, with a local read-only Streamlit dashboard and five interactive Plotly visuals. Display history for any catalog sensor and forecasts for the modeled target.

The official test period is 2026-08-08 23:00:00 through 2026-09-30 23:00:00 in source time. Dates and availability come from SQLite. Important demo cases include NK-76 casing pressure as inapplicable, NK-75 line pressure as applicable with zero test observations, and an older complete forecast release for NK-91.

## 3. Step-by-step development instructions

Before [SHARED CONTRACT READY](INTERFACES.md#shared-contract-ready), draft UI state cases and review the DDL and SQL interfaces. Start U01 after sign-off. Use temporary fixture DBs.
1. **U01.** Open SQLite in read-only mode so a bad path cannot create a new empty file. Use bound values in SQL. Allowlist table names and sensor columns when the query needs a SQL identifier. Return sorted data frames. Use `series_catalog` for well type and sensor choices. Use wide timestamps as the calendar and left join long for hourly values. Return the raw published value, `n_obs`, `flag` and `is_usable` alongside the display value. In clean mode blank out the displayed value of masked rows while retaining audit context. Use Student 1's SQL for gaps and aggregates. Until A05, exercise EDA and UI with contract-shaped outputs at the query boundary and defer tests that execute those SQL files. Keep all final reads wired to Student 1's queries. Join issues to raw by source record when that reference exists. Read forecast data by the shared keys and treat missing required tables as an incompatible database and empty tables as an unrun forecast.
2. **U02.** Compute count, mean, median, sample standard deviation, min, max and quartiles by well, parameter and unit. Use SQL daily/monthly aggregates for trend lines. Calculate hourly medians and quartiles with count from the chosen mode's values. Compare values across wells for the same parameter and unit. Compare both well types using observed, usable and flagged counts with explicit denominators. To combine daily sensor coverage across a type, sum expected and observed counts across applicable pairs before dividing. For correlations, form a timestamp-aligned frame for the selected well. For each parameter pair, take rows where both are present, compute Spearman from pairwise ranks, and report the actual count. Suppress the coefficient below 30 pairs or when either paired series is constant. Use raw mode for a faithful view of anomaly periods and apply date filters before statistics.
3. **U04.** Set up History and EDA, Data Quality, and Forecast and Evaluation. Sidebar order is type, well, parameter and date range. Limit child selections to valid catalog values after a parent changes. Default to the last 14 calendar dates through archive end. Convert the selected end date to midnight of the next day for SQL. Enable same-parameter, same-unit well comparisons. Provide raw/clean and day/month controls in the EDA view. The quality view shows full gap lengths, observed/expected and flagged counts, issue details and applicable event shortcuts for May area scale and June NK-7. Include before/after summaries using published observations and explicit periods. Keep the current selection visible when no data falls within it.
4. **U03.** Create four Plotly figures. History shows hourly values and trend, with breaks at missing hours and flags in hover or markers. Show event markers for the selected applicable row. Hourly profile shows the median, IQR and sample count by local source hour. The correlation matrix exposes the paired count in hover, including suppressed cells where practical. Coverage heatmap shows day by well for the selected sensor, plus a type-comparable all-applicable view with expected, observed and flagged counts. Use a distinct state for inapplicable sensor pairs and numeric zero for applicable pairs with no rows.
5. **U05.** Build a fifth figure with top timeline and lower MAE by horizon, plus a compact table with MAE, `n_common` and coverage. In backtest mode query by well, parameter, selected horizon, models and `target_ts` within selected dates. Use observed history for the factual line and keep it visible where predictions are absent. Show the forecast against actuals on aligned timestamps. Label the MAE panel with the entire official test period. Keep it available when the date selection misses test. In latest-release mode show up to 24 stored target points per selected model at the single shared origin. Build the time window around that origin, show the end of archive, and add recorded facts where the trajectory overlaps available history. Show the origin hour and its age relative to `test_end`. The release is stale when `origin_ts < test_end`. Use model toggles in both modes and apply the horizon selector to the backtest timeline. For non-`pump_fillage` choices explain forecast scope while history remains available. Distinguish an absent database, missing/unpopulated results, a supported well with no release and a valid selection without observations. Empty official metrics indicate no published result set. A supported well with metric rows and no path rows has no available release. Display NULL MAE as unavailable with counts and coverage. Distinguish a horizon with zero common keys across test from a nonempty horizon with no predictions in the date slice. Follow the [UI state acceptance table](DASHBOARD_PLAN.md#интеграция-и-состояния). Use official test metrics from SQLite without recalculating them from the visible date slice.
6. **U06–U08.** Switch from test DB to the official build for acceptance. Verify visuals interact in the browser and compare numbers to SQL, including one metric group checked with Student 2. Rehearse the documented sequence with both well types, NK-75, a quality event, correlation, a horizon switch and a dated forecast release. Use the same build for any screenshots and live demonstration.

## 6. Testing

### Synthetic fixture and component checks

- Run `python -m pytest tests/test_ui.py`. Use temporary SQLite and Streamlit test support where available for widget transitions. Assert read-only connections, parameter binding, inclusive end dates after conversion, stable catalog under empty dates, correct gap overlap, raw/clean display with zero, and no file creation for a missing DB. Verify a date window outside test leaves MAE queries intact.
- Construct an EDA fixture with different gaps in two series, at least 30 shared non-constant observations for a calculable result, and separate constant and small-sample cases. Check correlation and paired count, profile medians and quartiles, and weighted-by-expected type coverage against hand calculations.
- In temporary DB copies, exercise every [UI state](DASHBOARD_PLAN.md#интеграция-и-состояния). Include an incompatible schema, empty result tables, unsupported pressure target, no common keys at one horizon, a populated horizon with no keys in the date slice, and supported wells with missing, stale and current releases. Verify history and official MAE remain available where appropriate.

### Official data and integration checks

- Exercise NK-76 casing inapplicability, NK-75 line-pressure test gap, both anomaly shortcuts, and NK-91 release at 2026-09-29 09:00:00. Verify the release uses 24 points per selected model when available and remains labeled when archived actuals overlap.
- Run the app from a clean environment against the populated DB. In a browser verify all five figures, hover and zoom, toggling models, switching horizon, dates, source-time labeling and unit display. Compare an EDA statistic and one MAE/count row against the same SQLite file. Share U06 results with Student 2 for M07 and U07 results with Student 1 for A07.
