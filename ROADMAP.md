## Календарь

- **Неделя 1.** Утвердить контракт. Проверить загрузку и основные правила качества. Начать признаки и baseline. Поднять чтения SQLite и каркас Streamlit на fixture.
- **Неделя 2.** Закончить pivot и SQL. Сверить EDA и графики истории. Подготовить Ridge и провести внутреннюю валидацию.
- **Неделя 3.** Зафиксировать конфигурацию. Выполнить backtest и сохранить выпуск. Подключить приложение и начать сверку UI с БД. Параллельно завершать компонентные тесты.
- **Неделя 4.** Пройти сквозной сценарий, повторный запуск и проверку на чистом окружении. Запланировать последнюю рабочую сессию под исправления и генеральную репетицию.

Критическая цепочка для прогнозной демонстрации — A01 → A02 → A03 → A04 → диагностика и полный M03 → M04 → M05 → U06 → M07 → A07 → защита. В A07 также сходятся A06 и U07. Ветка U01 → U02 → U03 → U05 нужна до U06. Узкие места — совместный review A01, готовность SQLite для диагностики, A05 для сверки SQL и M05 для проверки UI. Время диагностики, проблемы с версиями и непредвиденные ошибки качества могут сдвинуть график. Студент 1 координирует A07. Каждый владелец исправляет дефекты своего модуля. Порядок PR и разрешения конфликтов указан в [INTERFACES.md](INTERFACES.md#github-integration). Если задерживается реальная БД, разработка UI продолжается на fixture, а M01–M02 проверяются на часовом ряде из fixture. Если задерживаются прогнозы, история, SQL и качество принимаются по своим критериям, а интеграция прогнозов завершается до защиты.
